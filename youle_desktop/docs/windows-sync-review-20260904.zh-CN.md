## 需要修复的问题

### 1. [P1] 全部行情请求失败后，旧价格仍能被包装成当前 K 线

位置：`src/renderer/trading-expert-market.ts:11734`，同一方法的 `11761`、`11770`。

`refreshCurrentMarketSnapshotForAnalysis()` 在三次 K 线请求、两次统计请求都失败后，仍回退到没有新鲜度证明的 `this.stats.midPrice` 或 `targetMarket.markPrice`，随后用 `Date.now()` 调用 `applyTradingLivePriceToBatch()`。最后的检查只看最后一根柱的时间，因此刚合成的柱必然看起来是当前行情；旧历史中的缺口也没有被补齐。

本地复现：输入三天前的 100 根一小时 K 线、没有 WebSocket 报价、所有网络请求抛错；方法成功返回 101 根柱，末柱为旧价格 123、成交量 0，中间缺 71 根小时柱，`tradingAnalysisCandlesRequireCurrentRefresh()` 返回 false，结果还被写回缓存。由此，界面所说的“强制刷新当前行情”不能保证分析获得当前事实。

修复方向：保留报价的真实事件时间和接收时间；没有有效当前报价时拒绝当前分析，不能给旧值重新盖当前时间。补齐并校验历史连续性后，才允许作为完整行情快照进入分析；单点报价只能作为有明确来源和覆盖状态的补充。

### 2. [P1] 刷新期间切换币种，会把分析任务与目标元数据混在一起

位置：`src/renderer/trading-expert-market.ts:10435`；同类路径在 `11060`、`11333`。

缠论、威科夫和订单流入口新增 `await refreshCurrentMarketSnapshotForAnalysis()` 后，没有重新校验选择或读取它返回的局部快照，而是继续读取可变化的 `this.candles`、`this.selectedMarketId`、`this.selectedSymbol`。刷新方法在目标已切换时不会提交旧目标的结果，但调用者仍继续创建任务。

本地对三个入口分别复现：明确请求 `BTCUSDT`，刷新等待期间把工作区切成 ETH；继续执行后生成 `job.symbol=ETHUSDT`、`job.marketId=BINANCE:FUTURES:ETHUSDT`，但 `job.market.symbol=BTCUSDT`。因此请求目标、行情和报告/绘图元数据不再一致。通用入口已经有刷新后的检查，可作为修复参照。

修复方向：使用发送时锁定的目标和返回的 candle batch 创建任务；或在 await 后检查 generation、市场及周期，一旦变化就取消当前请求。三个入口需要一并覆盖。

### 3. [P2] 新引导示例的 1:1.5 会被保存成最低盈亏比 1

位置：`src/renderer/main.ts:46657` 的新引导文案，以及 `46869` 至 `46872` 的解析器。

本次将建议格式改成 `1:x`，并向用户展示“1.5R后保本，最低盈亏比1:1.5”。但旧 `rewardRiskMatch` 仍优先匹配 `数字:1`；正则中的 `1\b` 也能匹配 `1.5` 的整数部分，因为小数点是词边界。因此该输入先匹配到 `1:1`，覆盖了正确的 `riskRewardMatch=1.5`。

执行现有解析器，得到 `breakEvenTriggerR=1.5`、`minimumRiskRewardRatio=1`，而用户要求的是 1.5。该值随后被写入个人风险约束，降低用户明确设置的最低要求。

修复方向：一次完整解析冒号两侧的数值，再依据约定转换；旧格式兼容不能接受小数的部分匹配。至少覆盖新文案本身、`1:0.4`、`1:1.3` 和原 `3:1`。

### 4. [P2] 当前波浪分析用父柱开盘时间截断低周期数据

位置：`src/renderer/trading-expert-market.ts:10763`、`10790`；分屏同类路径在 `10958` 附近。

`analysisEndTimeMs` 取最后一根父周期 K 线的 `time`，这个字段是开盘时间。当前行情分析也把它作为 `fetchTradingWaveDegreeContexts()` 的截止时间，因此会丢掉当前父柱内部已经收盘的子周期柱。防止历史回看访问未来数据的限制，被错误套到了当前行情请求。

本地复现：快照时间为 15:30 UTC，4H 当前柱从 12:00 开始；代码把子周期请求截止时间设为 12:00。模拟已有完整闭合行情时，1H 上下文缺少 13:00、14:00 两根，15m 上下文缺少 12:15 至 15:15 共 13 根。主周期包含新价格，执行子浪却仍停留在更早的状态。

修复方向：当前分析以实际快照时间截断已收盘子柱；历史窗口以 `min(snapshotTime, 最后父柱结束时间)` 为上界，不能直接使用父柱开盘时间。

### 5. [P2] 网关背压恢复后会先发新报价，再发旧报价

位置：`../services/haolo-binance-gateway/src/public-server.mjs:341`。

报价 A 在软水位以上时进入 `pendingMarketFrames`。如果 socket 缓冲在 25ms 定时器执行前降下来，报价 B 会走直接发送分支，但 A 没有被删除或替换；定时器随后继续发送 A。客户端因此收到逆序的 ticker、markPrice 或 K 线更新。

本地调用实际 connection 回调：先令 `bufferedAmount=600000`，输入事件 1/价格 100，再降到 0 并输入事件 2/价格 200；实际发送顺序为事件 `[2,1]`、价格 `[200,100]`。只订阅 ticker 等流且没有额外时序保护的消费者会回退到旧状态。

修复方向：恢复直接发送时处理同流已有 pending 值，保证每个流发送事件的时间单调；增加水位跨越期间新旧帧交错的行为回归。

### 6. [P2] 活动发布状态缺失或不完整时，watchdog 仍会重启旧实例

位置：`../services/haolo-binance-gateway/deploy/single-node/gateway-watchdog.sh:43` 至 `47`。

仅当解析出的 `active_container` 非空但容器不存在时，脚本才拒绝回退。状态文件丢失，或状态文件只有新端口而缺少有效 `CONTAINER` 时，变量为空，仍执行旧 Compose 的 `restart gateway`。后一种情况尤其明确：健康检查使用新端口，修复动作却操作旧容器，活动实例不会恢复。这也不符合 `SEAMLESS_DEPLOYMENT.md` 声明的状态缺失时拒绝旧实例回退。

以临时目录及 PATH mock 运行原脚本，分别复现状态缺失和仅含 `PUBLIC_PORT=18787`、`PRIVATE_PORT=18788` 的状态，两者都触发旧 `restart gateway`；不完整状态下最终返回失败。没有调用真实 Docker、服务或生产端口。

修复方向：在检查和重启前完整验证活动容器及端口；若需要兼容首次初始化，应有明确的 legacy 模式或首次初始化证据，不能把所有解析失败都视为旧部署。
