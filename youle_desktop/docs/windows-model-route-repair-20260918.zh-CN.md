# Windows 模型通道错配修复（M1-313）

2026-09-18：源码修复和验证完成，尚未打包、安装、推送或发布。网关配套改动也未部署。Mac 用户的另一起分析反馈不在本次验收范围。

## 原因

Windows 捆绑内核 0.153.4 对已订阅或错误态任务执行 `thread/resume` 时，可能接受新的模型设置，却继续使用原提供方及其凭据。普通发送入口没有验证返回的实际提供方；自动备用期结束后发送 Sol，以及反向转入 DeepSeek 时，都会因此将模型送进错误的 Key 分组。网关正确拒绝了请求，但原错误文案把通道错配也描述成“模型未启用”，且权限检查发生在模型/请求类型记录之前。

之前的恢复工具本身能够切换提供方，普通发送却未接入该工具。这解释了局部恢复测试通过而 Windows 仍出现错配的情况。本次回归直接执行实际 `codex:sendMessage` 处理函数。

## 实现

- 普通发送、自动恢复、设置/压缩、自动任务和保留的工作流终验入口共用提供方确认路径。GPT 未显式携带提供方时明确选择 `haolo_ai`，不沿用线程的 DeepSeek 通道。
- 只使用原生返回的 `modelProvider` 确认通道，不再根据模型名推测。提供方不一致时先解除订阅再恢复；仍不生效时仅在共享内核空闲时冷恢复。保留同一任务、历史、开发者指令、沙箱和推理配置，不发送探测模型请求。
- 新建、尚无历史文件的内存任务读取实际元数据验证通道。通道未知或不一致时拒绝发送，不删除或替换历史，也不重启忙碌内核。若新任务在第一条消息前恰好跨过备用期限且通道已变，需新建任务后发送；本次选择保留原任务并明确失败，避免以未经验证的通道调用模型。
- 一小时备用期到期时，连同旧缓存中的 DeepSeek 提供方和最高推理设置一起恢复。即使模型选择器已显示 Sol，也会清除残留提供方。
- 只读分析的临时任务也在发送前验证实际提供方，失败仍执行临时任务清理。
- 原生包装、嵌套错误以及只保留文本的错误中的 403/通道拒绝，均不能触发模型重试或伪装成成功的本地分析降级。
- 网关保留既有 403 权限边界，通道错配新增 `MODEL_ROUTE_GROUP_MISMATCH`，`category=policy`、`retryable=false`；在模型池校验前记录实际模型及请求类型，覆盖 HTTP、WebSocket 和媒体入口。
