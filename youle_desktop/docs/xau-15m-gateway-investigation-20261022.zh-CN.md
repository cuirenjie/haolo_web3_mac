# XAU 15 分钟 K 线超时调查（2026-10-22）

## 结论

已确认持续故障发生在香港行情网关对以下请求的共享刷新任务：

```text
/fapi/v1/klines?symbol=XAUUSDT&interval=15m&limit=501
```

该请求对应的共享任务长期不结束，Redis 刷新锁由同一持有者持续续期，但没有生成结果缓存。网关进程把后续相同请求合并到未结束的 Promise，导致调用者反复等待。客户端执行预算为 50 秒，因而显示截图中的 `Binance network request timed out after 50000ms`；生产 HAProxy 在约 60 秒后记录 504、`sH--`、上游响应头时间 `-1`。

这是已由现场状态、请求对照和源码共同确认的持续故障机制。首次刷新为什么停在某个异步步骤，目前没有该任务的阶段日志或调用栈，尚未确认。不能进一步将最初触发点写成已证实的币安网络中断、Redis OOM、鉴权故障或特定 Node.js 缺陷。

## 代码原因与隔离复现

`services/haolo-binance-gateway/src/cache.mjs`：

1. `singleFlight`（251 行）对相同 key 直接返回已有 Promise，只有 Promise 结束后的 `finally` 才删除 `inflight`。
2. `sharedSingleFlight`（258 行）中的 `deadline` 只限制争抢锁的循环。获得锁后，直接等待 `factory(controller.signal)`（297 行），没有覆盖整个任务的硬截止时间。
3. 续租定时器（281 行）持续刷新 Redis TTL，只在 factory 结束或协调失败后停止。一个未结束的任务因此可以长期占有该 key。
4. `binance-rest.mjs` 的 10 秒定时器从上游 fetch 前才启动（348 行），只发出 abort；它不能替代整个刷新流程的强制结束保证，也不覆盖此前缓存读取和准入等步骤。

使用未修改的生产同版 `GatewayCache` 和内存 Redis 替身，令 factory 暂停，配置 150ms 租约，等待 500ms：任务依然 pending、`inflight` 仍存在、已续租 8 次；相同 key 的新 factory 未被调用，改变为 `limit=500` 的独立 key 可立即完成。显式解除暂停后，两位调用者才一起返回。该复现证明持续故障机制，不代表确认了生产最初停在哪个 await。

复现命令（Windows 仓库根目录执行）：

```powershell
node youle_desktop/.cache/xau-15m-investigation-20261022/reproduce-flight.mjs
```

结果：断言通过，证据为同目录 `reproduce-flight.json`。不连接或改写生产 Redis。

## 修复方向与本次边界

根治应在网关共享刷新层增加覆盖整个操作的总时限，在超时后停止续租、终止旧操作并安全释放本任务的锁和内存占位；同时防止旧任务迟到后覆盖新缓存或删除新任务的占位，补充阶段和超时诊断。回归需要覆盖挂起的准入、fetch/正文、Redis 操作、相同 key 的后续重试及迟到结果隔离。

只延长客户端 50 秒超时不能消除挂起任务；只改请求数量是绕开当前 key 的诊断手段，不能视为根治。生产恢复需依照发布规则评估受控的新实例切流与旧连接处理，不能直接清空 Redis 或强杀连接。

调查阶段完成只读生产排查、客户端请求对照、源码核验和隔离复现，当时未修改产品代码或切换流量。

## 后续修复状态（2026-10-22）

用户随后要求彻底修复，网关代码已提交并推送：为共享刷新增加硬截止时间、停止无限续租、隔离迟到结果与旧版缓存锁。精确候选镜像通过 104/104 项真实 Redis 回归；候选中的原样 XAU 15m / 501 根请求恢复为 200，500 根已收盘 K 线与币安直接上游一致，WS／CONNECT 验收通过。
