# M1-453：Windows／移动端计划卡片一致性排查

日期：2026-10-22。结论：当前实现不能保证两端同时分析同一市场、周期时产生完全一致的计划卡片。已定位分析输入窗口差异，并实测价格显示精度差异；本轮为诊断，未修改产品代码或发布。

## 核验范围和版本

- Windows：规范仓库 dev，检查起点 `8a0a33a6990e757646deda66cd119c9a5a0df060`，package 版本 `0.1.179`，包含当前工作区。发现 Electron 开发进程来自规范仓库；没有重启或断言进程已加载所有最新主进程文件。
- 移动：规范仓库 dev，`6bcb2597aab5b80809a2be05baa1680269b80fb3`，包含既有未提交改动；pubspec 为 `0.1.7+8`，ADB 只读查询当前模拟器安装包亦为 `0.1.7 / versionCode 8`。没有操作界面、构建或安装。
- 后端本地检查起点 `768a059a84f37f15235c7ca3badfa2b1781e8d11`。SSH 实时核验 API green 与独立策略 Worker 均为 `8867c856cb978f1c4a281f5fa9a268724d11ce8c`。两端各九个相关运行文件与本地 SHA-256 一致：api、analysis_window、analysis_history、contracts、market、price_action、entry_policy、entry_projection、model_recovery。
- 只读访问生产容器版本和上述文件哈希；没有读取用户凭据、账户明细，未创建生产分析、计划或预警，没有付费模型调用。结论不是双端同时点击后的在线结果实测。

## 一、共同部分已经对齐

Windows `src/main/trading-strategy-runtime/cloud-runtime.mjs` 与移动 `apps/mobile/lib/data/live/trading_preferences.dart` 的新官方策略均发送 `clientContract=windows-v1` 和 `executionPolicy=entry-v2`，冻结账号级偏好 revision。这里的 windows-v1 是结果合同，不是设备类型。

服务端共用 `app/mobile/price_action.py` 的策略、模型审阅、入场决策和 `entry_projection.py` 投影。移动消费同次 `desktopResult.cloud.planRecords`，校验计划／情景／条件绑定；Windows 消费同一结构化结果。没有证据支持“手机仍使用一套独立旧算法”的判断。

对仓库内 102 份完整计划投影（17 策略 × 左右侧 × 三语）逐项比较：Windows 使用的条件入场边沿与移动 scenario.entry 全部相等，止损与全部止盈字段也相等。该检查证明这批相同冻结结果的核心原值对应一致，不证明两端独立运行会生成相同结果，也不证明所有历史协议和显示文本都相同。

## 二、独立分析的输入窗口不同

Windows `cloudAnalysisWindow` 默认 preferredCount=100，同时取可见 K 线数量和策略最低需求的较大值，最多600；`cloud-runtime.mjs` 再读取服务器最低需求。非显式时间范围下，威科夫额外建议240根，图表形态建议600根。

移动 `live_controller.dart` 为 ICT/SMT 和各指标（含VPVR）请求500根、订单流200根、其他600根；VPVR另带屏幕可见范围，服务端以该确切范围为准。移动不发送 Windows 的 windowCount／preferredWindowCount／lookbackMs。服务端 `analysis_window.py` 确实按 Windows 提交的窗口裁切，不会自动把两者归一为同一历史长度。

| 典型默认入口（Windows可见数量未超过默认值） | Windows | 移动 |
|---|---:|---:|
| 裸K、缠论、谐波、江恩 | 100 | 600 |
| 均线、MACD、RSI、KDJ、布林带、ICT/SMT | 100 | 500 |
| 道氏 | 120 | 600 |
| 订单流 | 120 | 200 |
| 威科夫 | 至少建议240 | 600 |
| 图表形态 | 建议600 | 600 |
| VPVR | 各自可见范围 | 各自可见范围 |

这是常规入口对比，不是所有请求都固定为表中数量；显式历史范围、更宽视口、服务器发布的更高最低需求和策略后续补取会改变实际输入。波浪另有多周期补历史，不能只靠初始数量判断最终上下文。

隔离控制实验固定同一行情序列、最后一根、快照时刻、策略和方向，只截取不同历史长度。20组既有合成引擎样本中，12组原生候选的存在性或价位发生变化。例：裸K空头样本196根与最后100根的入场、止损相同，第一目标分别为 `166.920595313` 与 `164.835988724`；多头同源样本从有候选变为空候选。此处是原生候选回放，不是线上完整模型／风控后的最终卡片，不能把12/20当作真实用户差异发生率。

## 三、同一冻结计划仍有显示差异

实际调用两端当前价格格式化函数：

| 原值 | Windows | 移动 |
|---:|---:|---:|
| 82292.3 | 82292.30 | 82292.30 |
| 123.4567 | 123.4567 | 123.46 |
| 9.123456 | 9.123456 | 9.1235 |
| 0.123456 | 0.123456 | 0.1235 |
| 0.00001234 | 0.000012 | 0.0000 |

Windows `execution-plan-card-view.mjs` 依据整数位数补足约七位数字；移动 `price_format.dart` 以价格小于10保留四位，否则两位。两者都只是显示处理，不改原始浮点数据；移动低价品种可能因此显示为零。相同盈亏比1.5，Windows结构化卡显示 `1:1.50`，移动去除尾零后显示 `1:1.5`。

另有展示语义差别：移动待执行草案可显示本地时区的“有效至”；当前 Windows 结构化卡正文不输出有效期，完整文本仍保存 UTC 期限，菜单／分享另有展示。这不是计划原始到期时间被改写，但不能称卡片内容完全相同。

历史计划还存在不同兼容保护：Windows 对旧 scenario.entry 与条件区间边沿不一致的记录显示当前边沿、隐藏对应估算并提示旧基准；移动直接使用冻结 scenario.entry。102份本轮完整计划没有此异常；不将其扩展为全部旧记录已一致。

## 四、同一时间并不是同一冻结分析

- 两端分别生成 clientRunId 和幂等键，独立取快照、提交任务；服务端没有按“同账号＋同市场＋同周期”自动返回同一分析结果。现有模型审阅检查点按 job ID 与审阅序号缓存，仅供原任务恢复。
- 同一交易对还需同市场类型，例如现货与USDT永续不同；也需同策略、提示词、语言、左右偏好及风控配置版本。
- 账户快照、多周期／订单流补取、估值时间按各任务冻结。选中同一账户也不表示取得同一毫秒的权益、仓位和盘口数据。
- 模型参与候选选择与等待判断，独立模型审阅没有相同输出保证；手选模型或恢复到备用模型也可能改变路径。不能把“共用引擎”解释成每轮模型审阅必然相同。
- 有效期由 snapshot.fetchedAt 加 validityBars 计算；即使价位相同，不同冻结时刻的期限、计划ID、条件哈希仍可能不同。

## 验证和建议

本轮 Windows云端运行／卡片／账户展示回归100/100；移动偏好、冻结结果、计划恢复及止盈显示回归82/82；两组均零失败零跳过。102份投影核心价位对应检查无差异，20组窗口敏感性回放中12组候选不同。额外价格格式化直接使用 Node 与 Dart 的真实产品函数。证据与复现脚本位于 Windows 根目录 `.cache/plan-parity-M1-453/`，包括 `probe.json`、`mobile-formats.json`、`runtime-evidence.json` 和两端测试日志。

建议先统一服务端定义的每策略历史窗口、截止时刻和VPVR可见范围语义，再统一价格／盈亏比显示精度。若产品要求同账号、同一冻结市场与账户输入下两端必须拿到完全相同的计划，应定义稳定分析指纹并复用同一冻结结果，而不是要求两次独立模型分析偶然相同。指纹需包含策略／算法版本、市场快照、账户快照、偏好版本、问题与模型执行策略；不得跨账号复用私人账户结果。
