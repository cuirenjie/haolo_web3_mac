## Windows 源码行为

- 同一会话、URL、请求头和读取模式的并发后台 GET 共用一次请求，各调用者持有独立响应和取消信号；最后一位取消才中止底层传输，取消覆盖响应正文读取。账户、语言、写入代次、主动刷新均隔离。
- 设置、联系人和手工画线持续不变时逐步降频。设置/联系人最多 30 秒，画线最多 15 秒；已有可信变更流健康时优先使用版本通知，版本变化或通知租约过期强制 REST 校验。没有把缓冲 SSE 当成新鲜通知。
- 设置主动同步、画线唤醒/待上传前读取、写入回读、联系人可见页面刷新绕过静默缓存。实时行情、分析进度、计划生命周期和提醒顺序读取不使用静默 TTL；计划/提醒的重叠 GET 可合并。
- 同一路由和身份的 429/503 共享 Retry-After 冷却，连续失败指数退避并带抖动；冷却不把失败伪装成成功或旧数据。前台交易偏好 PATCH 不进入此 GET 合并器，不自动重放其他写入。
- 交易偏好适配器单独识别 `503/MOBILE_BUSY/scope=db_pool`：只对 GET 和带原幂等键/冻结正文的偏好 PATCH 有限等待。数据库拒绝可能发生在处理器的早先事务已提交之后，耗尽时保留“结果待确认”，不误报“尚未保存”；其他 503 不获得自动重放权限。
- 手工画线明确 422/413 经受限 IPC 返回拒绝位置，不传递 Pydantic 的用户输入。拒绝项按 changeId 留存在本地，重启/后台 outbox 不再重发同一个永久无效修改；兼容项继续同步，用户编辑产生新 changeId 后可再试。旧的大批次 413 可重新分批；新批次控制 UTF-8 请求正文不超过 240,000 字节，单条过大数据留本机。
- 网络异常和提交结果不明仍保存原 mutationId、原正文；明确拒绝才允许重建批次。新提示具有简/繁/英/韩/日文，使用既有状态提示样式，不改变浅/深主题布局。

## 业务后端源码行为

- `trading-alert-feed` 的三个 SELECT 使用只读、可重复读事务。去掉原来不必要的用户写锁，保留多查询一致性；真实 PostgreSQL 测试覆盖持有写锁时仍可读取、并发写入不会破坏同一快照。
- Mobile Store 的连接池可按 API / Worker 分别配置；API 默认总上限仍为 5（含一个 LISTEN 名额），Worker 默认仍为 13。没有直接放大连接数或 HTTP 并发上限。
- 连接获取默认等待 API 5 秒、Worker 15 秒，获取失败返回明确 503/Retry-After，防止请求无限占位。只在尚未取得连接时转译；事务中的超时不伪装成安全准入拒绝。
- 每 30 秒有活动时输出有界聚合 `capacity_window`：并发峰值/限额、拒绝、响应码、耗时桶；数据库分连接等待、用户锁等待、事务占用。422 补充白名单字段/类型计数，不记录令牌、SQL 参数、账户、路径 ID、画线正文或验证原始输入。

## 验证与限制

- 隔离模拟 100 个账户、各 4 个读取入口、每 5 秒触发，2 分钟静默设置请求由基线 9,600 次降至 700 次（92.7%）；这是该固定模拟场景，不是生产收益预测。
- 100 个同时同账户读取合并成一次；单调用者取消、最后调用者取消、账户/请求头/语言隔离、主动刷新、写后失效、通知失效、429 冷却均有回归。
- 永久 422 outbox 连续触发 50 次只发一次读写；本地数据、后续编辑、其他有效图形、未知提交结果保持。
- 后端 96 个后台请求占满时，额外 1,000 次请求被有界拒绝，偏好 PATCH 仍获准；取消后计数归零。
- PostgreSQL 17 临时实例只绑定 `127.0.0.1:55478`，专用 `capacity_fixture`；未使用生产数据库。测试结束后该端口关闭。
- 本轮 Windows 专项回归 103 项通过；后端单元回归 33 项、真实 PostgreSQL 3 项通过；TypeScript、主进程语法检查及独立目录 Vite 构建通过。构建仅有既有大 chunk 警告，不等于 EV 安装包发布。两仓库客服候选知识包生成和运行时一致性检查通过。
- 历史 418 次 422 的具体输入字段未从旧访问日志确定。本次修复已确认的反复重放机制和请求体大小问题，并补充字段级聚合诊断；不宣称恢复了旧日志里不存在的请求正文。

## 发布后观察与扩容边界

需独立获得发布授权，分别核验 Windows 安装版本、API 和独立 Worker 的实际代码。老客户端继续原轮询，因此仅后端发布不能获得客户端模拟降幅。

发布后按相同流量窗口比较各类 GET/PUT 速率、429/422、P95、连接等待/锁等待、CPU/内存和数据库活动连接。若连接等待高但数据库有余量，先在所有连接池和滚动副本的总预算内调整；若连接等待低而单进程 CPU 持续饱和，再评估 API 副本。

源代码中的任务事件生产通道已经使用持久化 TaskStore，不能仅凭 `_TASK_EVENTS` 字典就判定多进程一定不安全。但 `app/lab/deployment.py` 的 split 角色仍约定每容器单进程，生命周期私有控制与发布排空也按该约定运行。因此本轮不把 `--workers 1` 直接改为 2；副本扩展须经现有受保护发布控制器、独立身份/排空和数据库预算验证。当前证据不支持先购买更多内存。
