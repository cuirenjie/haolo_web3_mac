# 交易偏好保存失败：根因与修复

日期：北京时间 2026-10-26。状态：源码修复和本地验收完成，尚未提交、推送、生产部署、发布安装包或重启用户开发版。

用户最终选择：**仅保留源码修复，暂不上线**。本次不执行后端部署或开发版重启；线上及当前运行中的客户端尚未加载本次修复。

## 故障证据

用户截图右下角时间为 14:30:09，设置页显示交易偏好保存失败。经现有香港 SSH 跳板只读检查生产 API 日志：

- 14:29:55.838：`PATCH /api/mobile/v1/trading-preferences` 返回 200。
- **14:30:06.477：同一保存接口返回 429，与截图失败时间吻合。**
- 14:30:17.771：同一保存接口再次返回 200。

访问日志不包含偏好正文或账号，以上是时间与接口关联；不将相邻请求的成功推断为截图账号已经完成保存。本机同时段日志存在持续的 `MOBILE_BUSY`。原始三行证据保存在规范后端仓库 `.incident/preference-save-20261026-access.log`，不提交用户运行数据。

## 根因

线上 `MobileAdmission` 的普通短请求名额被后台同步／轮询占满，偏好 PATCH 在进入路由、编译及数据库写入前即被 `429/MOBILE_BUSY` 拒绝。客户端设置保存原来只尝试一次；它将未映射的错误统一显示为“交易偏好保存失败”，因此界面看不出实际原因。

另一项尚未发布的 M1-466 分析入口修复已在共享工作区为偏好 GET 等分析入口划出受保护名额，但没有覆盖 PATCH。本次新测试在修改该遗漏前稳定得到 429，修改后在后台饱和的相同场景得到 200。因此只有分析入口修复仍不足以解决手动保存。

## 本次变更

- 后端严格将 `PATCH /api/mobile/v1/trading-preferences` 纳入前台受保护池，不扩大现有短请求总预算。不放开任意 PATCH、旧导入或其他路由；身份、输入大小、版本、编译租约及幂等检查保持在原处理链中。
- Windows 设置读取、保存、确认读取遇到明确 429/MOBILE_BUSY 时指数退避并遵循 Retry-After，单阶段等待预算 30 秒。复用现有 admission recovery，不改分析的 120 秒等待策略。
- 重试前固定保存正文、期望版本和幂等键；等待期间禁止重复点击和并发保存，每秒检查账号身份。版本冲突、权限、模型配额、未知网络提交不作为繁忙错误自动重复写入。
- PATCH 成功后仍需 GET 验证持久化结果。前次保存已受理或结果不确定时，后续繁忙不能把它重新描述为明确未保存；确认中断继续显示“结果待确认”。
- 持续繁忙有明确的五语提示，保留草稿和手动重试。主进程增加 `trading-preferences` 阶段／事件／错误码／状态日志，不记录账号、令牌、偏好内容或服务端原文。
- 两仓客服目录新增待发布说明并生成运行时及候选知识包，无新增代操作协议。
