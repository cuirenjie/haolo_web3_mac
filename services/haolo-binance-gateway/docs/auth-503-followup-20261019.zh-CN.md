# M2-027：12 次 503 归因与鉴权恢复修复

## 已确认的因果链

上一轮发布的 12 次行情 503 来自 Haolo `/api/auth/me` 鉴权等待超过网关的 5 秒截止时间。将候选容器的实际出口地址、HAProxy 接受时间和耗时关联后，12 次失败全部落在以下五次鉴权调用的开始时间加 5,000 ms 处，误差不超过 1 ms。共享同一会话的请求合并等待同一个鉴权结果，因此一次鉴权超时可以产生多次行情 503。

| 鉴权开始（UTC） | 最终耗时 | 最终 HTTP 状态 | 对应行情 503 |
| --- | ---: | ---: | ---: |
| 2026-10-18 15:58:37.731 | 5,062 ms | 200 | 1 |
| 2026-10-18 16:00:18.325 | 8,851 ms | 200 | 1 |
| 2026-10-18 16:00:21.220 | 6,059 ms | 200 | 4 |
| 2026-10-18 16:00:20.841 | 6,787 ms | 200 | 3 |
| 2026-10-18 16:00:31.108 | 5,886 ms | 200 | 3 |

这些请求在读取 Binance 行情之前失败，不能计作 Binance 429、Redis 配额拒绝或候选健康检查失败。相关窗口存在 578 次该候选发起的鉴权调用。证据保存在香港发布目录 `/opt/haolo/releases/market-m2-027-8935f3a/503-proven-auth-timeouts.json`，本机脱敏副本为 `youle_desktop/.cache/binance-503-followup-20261019/proven-auth-timeouts.json`。历史 72 次 504 的接受时间均早于上一轮切换。

现有证据能确认鉴权依赖延迟及网关超时的因果关系，不能进一步断言鉴权服务内部是数据库、线程池还是网络产生该延迟。本次没有修改业务后端，不能声称消除了后端延迟本身。

## 定向修复

1. 完整鉴权响应预算设为 10 秒，覆盖观察到的 5.06–8.85 秒尾延迟；生产显式环境变量和部署模板必须一起更新。
2. 截止时间覆盖响应头及 JSON 响应体。原实现收到响应头就清除计时器，后续响应体停滞可能长期挂起。超时会中止读取、返回有界失败，下一次请求可以正常恢复。
3. 过期进程内鉴权缓存立即重读 Redis，避免同一次读取错过另一个副本已写入的新鲜验证结果。鉴权 TTL 仍为 15 秒；无过期身份回退，无负结果身份缓存。
4. 503 增加请求关联 ID、`haolo-auth` 来源、超时/网络/上游状态/无效响应分类及计数。日志仅记录固定路由和错误类别，不记录凭证、查询参数、用户资料、票据或身份。
5. 客户端仍遵守原行情新鲜度、收盘状态和完整性校验；鉴权完成后才读取行情，不以旧价格换取成功响应。

## 测试及上线门禁

新增真实 HTTP 延迟重放：使用上表原始延迟和 1/1/4/3/3 个消费者，5 秒配置准确复现 12 次 503，10 秒配置全部返回当前行情。另验证响应体停滞超时后恢复、401/403/404 拒绝语义、上游 503/损坏 JSON/缺少身份不缓存，以及过期 L1 读取共享缓存。

上线以当前不可变镜像 `sha256:0c40ee03e2a67bb010c39dacc7d0bfa85df6f006798bef434d356f901d17eff9` 为基线，仅叠加本次四个运行时文件，保留现网认证基线。必须通过精确镜像与隔离真实 Redis 回归，再完成候选授权 REST/WS/CONNECT、受监督切换、公网与开发版分析数据复验。不要将本地完整 HEAD 中尚未上线的其他特性带入镜像。

旧实例 `haolo-binance-gateway-53badfa` 仍有既有 WebSocket。已安装独立守护检查，每 30 秒检查；确认活动路由不再引用旧端口、容器身份未变化，并连续两次同时满足下游 ESTABLISHED=0 和 WebSocket=0 后，才执行无限宽限的正常 stop。容器和镜像保留。代码见 `deploy/single-node/retire_drained_gateway.py`；服务为 `haolo-market-m2-027-drain-watch.service`；回执为原发布目录的 `retirement-status.json`。

旧连接未自然归零前，不叠加第三个生产网关、不强制断开；候选构建和隔离测试可先完成。生产显式超时仍为旧值，只有受控上线后才能宣称新修复已生效。客户端不打包、不签名、不发布。
