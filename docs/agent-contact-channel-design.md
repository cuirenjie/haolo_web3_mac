# 《有了》智能体通讯录与频道协作设计方案

## 1. 背景

现在桌面端已经有跨机器频道聊天的雏形：用户可以通过 email 或 citizen_id 搜索另一个账号，并把它加入频道。

但如果继续把这个能力理解成“把用户加进群聊”，后续业务会很容易混乱。因为《有了》的目标不是普通 IM，而是：

> 《有了》不只是桌面 AI 助手，还是数字生命通讯录。每个好友都是一个专业智能体：加好友就能调用它的技能，拉群就能让多个智能体协作，删好友就解除授权。未来，每个人都可以把自己的经验、提示词、数据和工作流封装成一个可售卖的智能体好友位。

因此，当前“搜索用户并加入群聊”的设计应该升级为：

> 搜索的是账号，加入的是智能体联系人，频道里参与的是角色，真正干活的是智能体，任务要和聊天分开。

## 2. 产品定位

《有了》的频道不是普通群聊，而是一个多智能体协作空间。

通讯录里的好友也不是普通联系人，而是一个可以被授权、调用、协作和售卖的智能体入口。

核心产品定义：

```text
《有了》 = 智能体通讯录 + 多智能体协作网络
```

## 3. 核心概念

### 3.1 User：真实用户账号

User 是真实登录身份，例如：

```text
caixikai02@gmail.com
mnm0756@gmail.com
```

User 负责：

- 登录认证
- 账号资料
- 会员/权限归属
- 好友关系归属
- 桌面端归属
- 智能体所有权归属

### 3.2 Agent：用户封装出来的智能体

Agent 是用户开放给别人调用的能力入口。

短期可以先给每个用户一个默认智能体：

```text
caixikai02
  - caixikai02 的桌面智能体

mnm0756
  - mnm0756 的桌面智能体
```

长期一个用户可以有多个 Agent：

```text
caixikai02
  - 产品经理智能体
  - 前端设计智能体
  - 投研智能体
  - 私人桌面执行 Bot
```

Agent 可以封装：

- 专业经验
- 提示词
- 私有知识库
- 工作流
- 本地工具能力
- 桌面端执行能力

### 3.3 Contact：智能体联系人

用户搜索另一个账号后，加入的不是一个普通 user，而是这个账号对应的“智能体联系人”。

例如搜索：

```text
mnm0756@gmail.com
```

搜索结果应该表达为：

```text
用户mnm0756
ID 11001 · mn***@gmail.com

将加入：
- 本人
- 桌面智能体
```

这里的“联系人”代表：

```text
mnm0756 这个账号
mnm0756 本人
mnm0756 的默认智能体
未来 mnm0756 开放出来的更多专业智能体
```

### 3.4 Channel：频道/协作空间

Channel 不是普通群聊，而是共享上下文空间。

一个频道里可以有：

```text
用户A 本人
用户A 桌面智能体
用户B 本人
用户B 桌面智能体
用户C 专业智能体
公开市场智能体
```

UI 可以简化显示为：

```text
mnm0756@gmail.com
2人 · 4角色
```

底层实际角色是：

```text
caixikai02 本人
caixikai02 桌面智能体
mnm0756 本人
mnm0756 桌面智能体
```

### 3.5 Actor：频道里的实际发言/执行角色

频道成员不是最小单位，Actor 才是。

一个用户加入频道后，至少会产生两个 Actor：

```text
User Human Actor
User Desktop Bot Actor
```

例如：

```text
caixikai02-human
caixikai02-desktop-bot
mnm0756-human
mnm0756-desktop-bot
```

Actor 负责：

- 谁在发言
- 谁被提及
- 谁被调用
- 谁执行任务
- 谁返回结果

### 3.5.1 P0 暂不建 Actor 表时的映射

P0 为了控制改动范围，暂时不新增 `channel_actors` 表。

当前用下面字段模拟 Actor 语义：

```text
sender_user_id：消息归属的真实用户账号
sender_type：这个账号下的发言角色
payload.source：发送角色语义
payload.target：目标角色语义
```

当前 `sender_type` 约定：

```text
user：用户本人
user_desktop_agent：该用户的桌面智能体
```

例如：

```text
sender_user_id = caixikai02
sender_type = user_desktop_agent
```

表示“caixikai02 账号下的桌面智能体在发言”，而不是普通云端 Bot，也不是对方账号。

未来引入正式 Actor 表后，可以迁移为：

```text
sender_user_id + sender_type -> sender_actor_id
payload.target -> target_actor_id
```

### 3.6 Message：普通沟通内容

Message 是聊天表达，不一定代表执行动作。

例如：

```text
caixikai02：这个需求我们这样做可以吗？
```

这只是普通消息。

### 3.7 Task：智能体执行请求

只要是“让某个智能体干活”，就应该创建 Task，而不是只存一条普通消息。

例如：

```text
@mnm0756 的桌面智能体 帮我检查这个项目为什么启动失败
```

底层应该表达为：

```text
requester_actor: caixikai02-human
assignee_actor: mnm0756-desktop-bot
task_type: desktop_agent_request
status: requested
prompt: 帮我检查这个项目为什么启动失败
```

## 4. 当前桌面端“搜索用户并加群”的设计调整

### 4.1 当前问题

现在的流程容易让用户误解：

```text
搜索用户 -> 把用户加进群
```

这会带来两个问题：

1. 用户以为频道名写成对方 email 就等于邀请了对方。
2. 后续人和 Bot 都在频道里说话时，无法区分谁在聊天、谁在执行任务。

### 4.2 新语义

应该改成：

```text
搜索账号 -> 邀请智能体联系人进频道
```

也就是说：

```text
搜索的是 User
加入的是 Contact
展开后得到 Human Actor + Agent Actor
```

### 4.3 弹窗文案调整

当前：

```text
添加成员
搜索用户
添加到频道
```

建议改成：

```text
邀请联系人
搜索 email 或 citizen_id
邀请到频道
```

### 4.4 搜索交互

不要在输入过程中自动搜索。

推荐交互：

```text
输入 email 或 citizen_id
点击“搜索”
或按 Enter 搜索
```

输入过程中只显示：

```text
输入完成后再搜索
```

不要在用户输入半截时显示：

```text
没有找到用户
```

这样更符合“精确搜索”的心智，也避免后端被频繁请求。

### 4.5 搜索结果展示

搜索结果不要只显示一个用户名称。

推荐展示：

```text
用户mnm0756
ID 11001 · mn***@gmail.com

将加入：
本人 · 桌面智能体
```

未来如果用户开放多个智能体，可以展示：

```text
可调用智能体：
- 桌面智能体
- 前端专家
- 投研助手
```

短期可以默认加入：

```text
本人
桌面智能体
```

### 4.6 创建频道规则

新建频道时，不允许只填写频道名称就创建。

必须至少选择一个搜索结果用户。

原因：

```text
频道名称只是名称
选中的联系人才代表真正邀请了谁
```

否则会出现：

```text
频道名：mnm0756@gmail.com
实际参与者：只有 caixikai02 自己
```

这种状态会误导用户。

## 5. 频道内角色模型

### 5.1 加入一个联系人后发生什么

当用户 A 邀请用户 B 到频道时，表面上加入的是：

```text
用户B
```

底层应该生成或关联：

```text
用户B-human
用户B-desktop-bot
```

频道里最终有：

```text
用户A-human
用户A-desktop-bot
用户B-human
用户B-desktop-bot
```

### 5.2 UI 展示建议

左侧频道列表：

```text
mnm0756@gmail.com
2人 · 4角色
```

频道顶部：

```text
mnm0756@gmail.com
2人 · 4角色
```

成员面板：

```text
caixikai02
  本人
  桌面智能体

mnm0756
  本人
  桌面智能体
```

### 5.3 不建议直接平铺所有 Actor

不要在主界面直接展示：

```text
caixikai02-human
caixikai02-bot
mnm0756-human
mnm0756-bot
```

这样会让普通用户感觉复杂。

推荐：

```text
普通 UI 显示联系人
高级交互时选择具体 Actor
```

## 6. 发送消息时必须明确目标

### 6.1 当前风险

如果频道里有很多人和很多 Bot，但输入框只有一个“发送”，业务会变乱：

```text
这句话是给所有人看的？
是给某个人看的？
是让某个 Bot 干活？
所有 Bot 都要响应吗？
```

### 6.2 推荐输入模式

输入框应该有一个发送对象选择器：

```text
发到频道
发给 mnm0756 本人
调用 mnm0756 的桌面智能体
调用 caixikai02 的本机智能体
```

默认：

```text
发到频道
```

当选择“调用某个智能体”时，按钮文案从：

```text
发送
```

变成：

```text
下达任务
```

### 6.3 普通消息

普通频道聊天：

```text
sender_actor: caixikai02-human
target: channel
message_type: chat
text: 这个需求我们这样做可以吗？
```

### 6.4 发给某个人

定向给某个人：

```text
sender_actor: caixikai02-human
target_actor: mnm0756-human
message_type: chat
text: 你看一下这个需求
```

### 6.5 调用某个智能体

调用对方桌面智能体：

```text
sender_actor: caixikai02-human
target_actor: mnm0756-desktop-bot
message_type: task_request
text: 帮我检查这个项目为什么启动失败
```

这时系统应该创建 Task。

## 7. Message 与 Task 必须分开

### 7.1 Message 的职责

Message 负责表达：

- 普通聊天
- 任务请求的可见文本
- 任务状态提示
- 任务结果摘要

### 7.2 Task 的职责

Task 负责执行：

- 谁请求
- 谁执行
- 执行什么
- 当前状态
- 权限是否允许
- 是否需要确认
- 执行结果
- 错误信息

### 7.3 Task 状态

建议状态：

```text
requested
waiting_approval
accepted
running
waiting_input
completed
failed
cancelled
rejected
```

### 7.4 任务消息展示

用户看到的不是一串普通气泡，而是任务卡片：

```text
任务：检查项目启动失败原因
执行者：mnm0756 的桌面智能体
状态：运行中

进度：
- 已收到任务
- 正在检查项目
- 发现 package.json 脚本异常
```

完成后：

```text
任务已完成
结果：问题在 xxx 文件，第 42 行...
```

## 8. Bot 响应规则

### 8.1 Bot 不应该自动监听所有消息

不要让 Bot 看到频道里所有消息后自己判断要不要执行。

必须满足以下条件才执行：

```text
被明确选择为目标
或被明确 @
消息类型是 task_request
权限允许
必要时主人确认
```

### 8.2 为什么要这样

如果 Bot 自动监听所有消息，会导致：

- 多个 Bot 同时抢答
- 普通聊天被误认为任务
- Bot 执行错误对象的指令
- 权限边界不清晰
- 跨机器执行风险过高

### 8.3 推荐执行规则

```text
发到频道：默认 Bot 不执行
@某个 Bot：该 Bot 可响应
选择“调用某个 Bot”：该 Bot 执行
任务卡片：只有 assignee Bot 执行
```

### 8.4 P0 的桌面智能体触发规则

P0 当前还没有正式的 @ 与 Task，因此只允许一种触发方式：

```text
payload.target.type == user_desktop_agent
payload.target.user_id == 当前登录用户id
sender_user_id != 当前登录用户id
```

不允许把“两人频道里对方发来的普通消息”默认当作给本机桌面智能体的请求。

原因：

```text
普通聊天会被误触发
多个客户端可能重复处理
未来多人、多智能体频道会混乱
权限边界不清晰
```

桌面智能体处理前必须先向后端 claim：

```http
POST /api/channels/{channel_id}/agent-claims
```

后端保证：

```text
同一条 message + 同一个 agent_owner_user_id 只能 claim 成功一次
```

这条规则用于防止：

```text
同一台电脑开两个客户端
SSE 重连重复收到事件
启动后历史消息补扫重复处理
本地乐观消息与远端正式消息重复合并
```

## 9. 桌面智能体权限边界

桌面智能体与普通云端智能体不同，它可能访问：

- 本地文件
- 本地项目
- 本地命令行
- Code CLI
- MCP 工具
- 用户私有数据

所以权限必须更严格。

### 9.1 默认权限建议

```text
普通聊天：允许
调用公开技能：允许
读取公开知识库：允许
读取本机文件：需要确认
执行命令：需要确认
修改文件：强确认
跨用户远程执行：默认强确认
```

### 9.2 好友关系不等于远程控制

加好友只代表：

```text
可以调用对方开放出来的能力
```

不代表：

```text
可以随便控制对方电脑
```

### 9.3 授权模式

建议至少有三种：

```text
只读模式
  允许分析、回答、读取已授权资料。

需要确认
  每次涉及本地环境、文件或命令时，需要主人确认。

自动接受
  对指定好友、指定频道或指定任务类型自动执行。
```

默认应该是：

```text
跨用户调用桌面智能体 = 需要目标用户确认
```

## 10. 好友关系与授权

### 10.1 加好友

加好友不是简单建立社交关系，而是：

```text
获得调用某个智能体的授权
```

### 10.2 删除好友

删除好友就是解除授权：

```text
不能再调用该智能体
不能再邀请该智能体进新频道
历史频道可按策略保留或禁用调用
```

### 10.3 邀请进频道

短期测试阶段：

```text
搜索用户 -> 直接邀请进频道
```

产品化阶段：

```text
如果已是好友：可以直接邀请
如果不是好友：先发送好友/频道邀请
如果调用桌面执行能力：仍需要目标用户确认
```

## 11. 商业化：智能体好友位

未来用户可以把自己的能力封装成可售卖的好友位。

售卖的不是聊天资格，而是：

```text
调用经验
调用提示词
调用数据集
调用工作流
调用工具链
调用专业判断
```

### 11.1 好友位等级

```text
免费好友位
  基础提问和简单回复。

专业好友位
  可调用专业技能和提示词。

高级好友位
  可调用工作流、数据集、模板和自动化流程。

企业好友位
  多人协作、审计、权限管理、知识库共享。
```

### 11.2 市场化表达

用户不是发布一个普通 Bot，而是在出售：

```text
一个可添加到通讯录的数字专业分身
```

## 12. 分阶段落地建议

### 12.1 P0：修正当前频道邀请语义

目标：

- 把“添加成员”改成“邀请联系人”
- 搜索 email/citizen_id 后手动触发搜索
- 新建频道必须选择联系人
- 加入联系人时，概念上加入“本人 + 默认桌面智能体”
- 左侧频道列表显示参与人数
- 使用 `sender_type=user_desktop_agent` 区分桌面智能体发言
- 使用 `payload.target=user_desktop_agent` 明确调用目标
- 使用 `agent-claims` 防止桌面智能体重复处理同一消息
- 使用 `client_message_id` 合并本地乐观消息和远端正式消息

暂时可以不真正拆 actor 表，但 UI 和业务语义要先对齐。

P0 消息显示规则：

```text
当前账号下的消息靠右，包括本人和本机桌面智能体
对方账号下的消息靠左，包括对方本人和对方桌面智能体
```

因此：

```text
sender_user_id == 当前登录用户id -> 靠右
sender_user_id != 当前登录用户id -> 靠左
```

发送方名称不能从频道标题反推，必须从频道参与者数据中按 `sender_user_id` 查找。

### 12.2 P1：引入 Actor 概念

目标：

- 后端区分 channel_participants 与 channel_actors
- 一个 user participant 自动拥有 human actor 与 desktop_bot actor
- message 增加 sender_actor_id 与 target_actor_id
- UI 支持查看成员下的角色

### 12.3 P2：引入 Task

目标：

- 调用 Bot 不再只是普通消息
- 创建 task_request
- Bot 通过任务事件执行
- 任务有状态、结果、错误、审批

### 12.4 P3：好友授权系统

目标：

- 加好友 = 授权关系
- 删除好友 = 解除授权
- 不同 Agent 有不同权限
- 跨机器桌面执行需要确认

### 12.5 P4：智能体好友位市场

目标：

- 用户可以发布自己的智能体
- 其他人可以添加/订阅
- 支持免费、付费、企业授权
- 支持调用统计、评价、收益分账

## 13. 当前桌面端改造重点

短期最应该改的不是复杂后端模型，而是先把用户心智改正确。

当前桌面端应该优先做到：

```text
添加成员 -> 邀请联系人
搜索用户 -> 搜索 email 或 citizen_id
添加到频道 -> 邀请到频道
输入过程不自动搜索
必须选择搜索结果才能创建频道
频道标题展示 2人/4角色 的方向
输入框未来支持“发到频道/调用智能体”
```

这样现在的跨机器聊天可以自然升级成智能体协作，而不会变成一套难以维护的普通群聊机器人系统。

## 14. 一句话原则

后续所有设计都可以用这句话判断：

```text
频道负责上下文，好友负责授权，智能体负责能力，任务负责执行，消息负责表达。
```

如果一个功能同时把这些职责混在一起，就说明设计需要拆开。
